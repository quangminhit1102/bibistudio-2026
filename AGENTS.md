- Catalogue data lives in `src/data/catalogue.ts` with product type and collection as separate dimensions; `/products/$slug` resolves type slugs to listings, otherwise product detail. Why: brand catalogue, not a shop — no prices/cart.
- Product imagery is normalized into `public/catalogue` with ASCII filenames; polished images lead and matching photographs follow in detail galleries. Why: predictable URLs, lighter pages, and consistent presentation.
- Journal imagery lives in `public/journal` and is assigned in `src/data/blog.ts`; listing cards stay square while article images render in a 3:2 frame. A seeded product or post stores the public path of its images (`/catalogue/...` in `image_ids`, `/journal/...` in `image_id`); `scripts/content-image-refs.mjs` plans and verifies that change for a database seeded earlier (`docs/content-image-refs.md`). Why: a database row can only name a file whose URL does not change between builds.
- Showcase motion primitives (Parallax, ScrollExpand, SplitWords, Tilt, FilmStrip, Magnifier) live in `src/components/brand/motion.tsx`; transform/opacity only and disabled under reduced motion. Why: one place for consistent, cheap, accessible effects.
- For local development, CI changes, deployment or rollback, read `docs/build-and-deploy.md` first; its status separates tested local tooling from live hosting acceptance. Why: a passing build does not prove a production deployment.
- Brand-specific values (name, domain, contact, SEO, fonts, theme tokens, logo) live in `site/` and core reads them only through `src/platform/site.ts`; `scripts/site-boundary.test.mjs` fails `npm run check` when a site value or a direct `@site/*` import appears in migrated core folders. Why: the core must stay reusable for other brands (`SITE_DIR` selects the site at build time).
- Product attributes (label, type, select options), per-collection grouping and what one collection's page adds (`collectionPages`: feature layout, quote, themes) are declared in `site/catalogue.config.ts` and read through `src/lib/catalogue-attributes.ts`; a product type or collection outside the known lists is shown by its own slug. Why: another brand declares its own attributes without editing core pages.
- Product types and collections are database records managed in the admin (`/admin/products/types`, `/admin/products/categories`); a product stores its type's `code` (never renamed) and its collection's `slug`, and the type's `slug` is only the public URL. Pages and admin forms read both lists from the API through `src/lib/catalogue-taxonomy.ts` and `useRelationOptions`, with `src/data/catalogue.ts` as the fallback when the API has none; the boundary test fails when core code names one of the site's types or collections. Why: a new type or collection is added in the admin, not in code.
- The home, about and contact page bodies live in `site/pages/` and reach their routes through `src/platform/pages/`; the routes keep only the loader and the head. Every text of the public interface is a key of `Messages` (`src/platform/site-contract.ts`) with its wording in `site/messages/vi.ts`, read through `t()` in `src/lib/messages.ts`. Why: another brand replaces these pages and texts by editing `site/` only.
- Each admin feature declares itself in `src/features/admin/<feature>/module.ts` (id, permission resource, owned paths, menu items) and is listed in `src/features/admin/modules.ts`; a site switches features on with `admin.modules` in `site/site.config.ts`. The menu is built from the manifests, `can()` refuses the resource of a module that is off, and the `/admin` route sends its addresses to the dashboard. The dashboard and a user's own profile and appearance pages are always on. Why: another brand takes only the admin features it needs without editing core.
- `tests/fixtures/site-blank` is the smallest site core accepts and switches every admin module on; `node scripts/check.mjs blank-site` (its own CI job) type-checks, runs the admin tests and builds with `SITE_DIR` set to it. Tests in `tests/admin` must hold for any site; what is true of one site only goes in `site/tests/`. A new text key or required site file is added to the blank site in the same change, and `node scripts/new-site.mjs` starts a site from it (`docs/new-site.md`). Why: a core change that needs the default site fails CI instead of the next brand's build.
