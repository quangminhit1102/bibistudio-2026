# BiBi Admin Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans or superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Build the complete master-prompt admin demo under /admin, with the approved Lovable visual direction and measured public-site performance isolation.

**Architecture:** Thin TanStack file routes lazy-load feature pages inside an admin-only shell. Typed async services backed by IndexedDB feed Query hooks and reusable accessible components; public catalogue and Express demo API stay independent. Deliver and verify incrementally, but completion requires every master module and showcase item.

**Tech Stack:** Existing React19, strict TypeScript, Vite CSR/TanStack Router+Query, Tailwind4, Zod3, Lucide, Express/Node24. Add only justified UI/table/form/chart/editor packages and dev-only test tools after compatibility verification.

**Spec:** ../specs/2026-11-01-admin-dashboard-design.md and ../specs/2026-11-01-admin-master-prompt.md. Read both; design resolves stack/integration conflicts, master retains full functionality inventory.

## Global Constraints

- Preserve current public refinements on codex/local-ui-refinements; no shared-history rewriting. Use an isolated named branch/worktree; detect existing managed isolation before creating anything.
- /admin namespace; router basepath / and /~vhplasti; no public header/footer/contact widgets in admin.

## File map and shared interfaces

Create src/features/admin/{shell,shared,services,demo,dashboard,analytics,products,bookstore,sales,accounts,content,audit,notifications,settings,showcase}; each feature owns pages/, components/, hooks.ts, models.ts, schemas.ts and service.ts only when needed. Do not create empty directories or generic screens standing in for full workflows.

Routes: src/routes/admin.tsx (thin lazy shell adapter), admin.index.tsx (redirect dashboard), admin.<group>.tsx/layout and nested route files following existing TanStack naming. Admin login uses a guard-exempt child route, not a second public application. Generated src/routeTree.gen.ts is regenerated by tooling, not hand-edited.

Shared contracts in services/contracts.ts:

- AdminModels maps entity keys to typed records; EntityKey=keyof AdminModels. Every record has id:string, createdAt:string, updatedAt:string and revision:number. Specific models add fields/invariants in owning tasks.
- ListInput<F>={page:number,pageSize:number,search?:string,filters?:F,sort?:{field:string;direction:'asc'|'desc'},signal?:AbortSignal}; ListResult<T>={items:T[];total:number;page:number;pageSize:number}.
- EntityService<T,C,U,F> exposes list(input), get(id,signal?), create(input), update(id,input,expectedRevision), remove(id,expectedRevision), bulk(action,ids), export(input), all Promise-based. ServiceError codes validation/not-found/forbidden/conflict/storage/aborted; pages never read storage directly.
- AdminStore: get<K>(entity:K,id:string):Promise<AdminModels[K]|undefined>; list<K>(entity:K):Promise<AdminModels[K][]>; transaction<T>(entities:EntityKey[],work:(tx:AdminTransaction)=>Promise<T>):Promise<T>; reset():Promise<void>. AdminTransaction gives typed get/list/put/remove within one transaction, no external await/network while transaction is active. Media blobs use separate blob store with transaction support.
- ServicesContext supplies an AdminServices object with typed per-feature services, session and demo clock. Http transport uses the same contracts; no real backend requests in demo mode.
- Query keys: ['bibi-admin',entity,'list',inputWithoutSignal] and ['bibi-admin',entity,'detail',id]; aggregate keys named by feature/date range; mutation invalidation explicit. Reset clears only bibi-admin cache keys.
- Theme='light'|'dark'|'system'; DemoSession={userId:string;roleId:string}|null. Preferences/session keys start bibi-admin:. DB name bibi-admin-demo, schemaVersion1. IDB schema changes must migrate or visibly offer confirmed reset.
